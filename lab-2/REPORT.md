Лабораторна робота №2

Мета роботи:
Метою лабораторної роботи було налаштування CI-конвеєра для модульного Python-проєкту за допомогою GitHub Actions.  
У ході роботи потрібно було:
- автоматизувати запуск модулів при `push` та `pull_request`,
- реалізувати ручний запуск workflow через `workflow_dispatch`,
- зберігати результати виконання як artifacts,
- навчитися запускати pipeline як на GitHub-hosted runner, так і на self-hosted runner.

Частина A — CI на GitHub-hosted runner
Було створено workflow-файл:

`.github/workflows/ci.yml`

Цей workflow налаштовано на запуск у таких випадках:

- `push` у гілку `main`,
- `pull_request` у гілку `main`,
- ручний запуск через `workflow_dispatch`.
Для реалізації запуску модулів було використано `matrix strategy`, що дозволило паралельно виконувати один і той самий job для різних модулів проєкту.

У workflow виконувались такі кроки:

1. `Checkout repository` — отримання коду репозиторію.
2. `Set up Python` — підготовка Python-середовища на GitHub-hosted runner.
3. `Install dependencies` — встановлення залежностей із `requirements.txt`.
4. `Create artifact directories` — створення службових папок для логів і результатів.
5. `Run selected module` — запуск відповідного Python-модуля.
6. `Copy generated files` — копіювання згенерованих файлів до папки artifacts.
7. `Upload artifacts` — завантаження результатів у GitHub Actions artifacts.

У результаті було успішно налаштовано CI-конвеєр, який автоматично запускає всі модулі:

- `data_load`
- `data_quality_analysis`
- `data_research`
- `visualization`

Частина C — запуск pipeline на self-hosted runner

Для виконання цієї частини було підключено self-hosted runner на локальному MacBook.

Було створено окремий workflow:

`.github/workflows/ci-selfhosted.yml`

Цей workflow запускається вручну через `workflow_dispatch` і виконує модуль `visualization` на локальному self-hosted runner.

Основні кроки workflow:

1. Checkout репозиторію.
2. Перевірка локального `python3`.
3. Створення ізольованого середовища `.venv-ci`.
4. Встановлення залежностей.
5. Підготовка локального датасету.
6. Запуск модуля `visualization`.
7. Завантаження результатів у artifacts.

У результаті було успішно виконано запуск workflow на self-hosted runner, що підтвердило можливість виконання CI/CD не лише у хмарному середовищі GitHub, а й на локальній машині.

Порівняння GitHub-hosted runner та self-hosted runner

### GitHub-hosted runner

Переваги:
- не потребує ручного налаштування інфраструктури;
- кожен запуск відбувається у чистому середовищі;
- швидко запускається і просто налаштовується.

Недоліки:
- не має доступу до локальних файлів користувача;
- залежить від зовнішніх ресурсів і мережевого доступу;
- при роботі з великими локальними даними менш гнучкий.

### Self-hosted runner

Переваги:
- має доступ до локальних ресурсів машини;
- дозволяє використовувати вже наявні локальні файли;
- дає більший контроль над середовищем виконання.

Недоліки:
- потребує ручного налаштування;
- runner може бути offline;
- можливі проблеми з архітектурою, Python-середовищем, SSL або PATH;
- відповідальність за підтримку середовища лежить на користувачі.

У межах цієї лабораторної було показано обидва варіанти запуску pipeline, що дозволило порівняти їх на практиці.

## Проблеми під час виконання роботи та їх вирішення

Під час налаштування CI/CD було виявлено кілька практичних проблем.

### 1. Відсутність `requirements.txt`
На початковому етапі workflow падав під час підготовки Python-середовища. Проблему було вирішено створенням файлу `requirements.txt` та коректним встановленням залежностей.

### 2. Залежність модулів від попередньо підготовлених даних
Модулі `data_quality_analysis`, `data_research` і `visualization` потребували наявності обробленого CSV-файлу. У CI це було вирішено підготовкою даних перед запуском залежних модулів.

### 3. Проблеми з checkout на self-hosted runner
Self-hosted runner не міг отримати код репозиторію через конфлікт локальної Git-конфігурації. Проблему було вирішено очищенням відповідних `git config` правил і виправленням налаштувань workflow.

### 4. Несумісність архітектур Python-середовища
На self-hosted runner виникла проблема через різну архітектуру локального середовища та runner-а. Рішенням стало створення окремого ізольованого середовища `.venv-ci` у workflow.

### 5. SSL-помилка при завантаженні датасету
Під час запуску `data_load.py` на self-hosted runner виникла помилка перевірки SSL-сертифіката. Для вирішення було використано локально підготовлений датасет, що також продемонструвало перевагу self-hosted runner — доступ до локальних ресурсів.

- автоматичний запуск workflow при `push` і `pull_request`,
